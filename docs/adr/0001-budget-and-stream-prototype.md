# ADR 0001：以 PostgreSQL 账本验证预算与流式终结

状态：原型采用，生产架构待后续验收。

## 背景

开源研究确认了供应商适配、预算预留与异步清理的必要性，但尚未证明本工程的并发和取消语义。第一轮实现聚焦这两个高风险机制，不扩展到管理端、认证和真实供应商。

## 决策

- Go 1.27.3，pgx v5.7.6；原型直接使用参数化 SQL，正式查询稳定后再评估 sqlc。PostgreSQL 测试镜像固定版本与 digest。
- 组织和项目预算在同一事务预留，先锁组织再锁项目；所有请求状态操作先按 request_id 获取事务级 advisory lock，避免重复预留/结算。
- 用整数模拟计费单位验证一致性；价格版本和预算周期与预留一起持久化，不使用真实币种或 tokenizer。
- 每次状态变更与 outbox 事件同事务提交；同一终态和金额的重复操作成功返回，不同金额冲突不得覆盖。
- 标记 dispatched 后才请求供应商；无法确认是否发送的情况保守保留占用。恢复只将遗留 dispatched 转为 uncertain，不自动释放 reserved。
- 客户端 context 负责取消上游；独立的有界 context 负责终结。正常上游 usage 与 DONE 齐备且数据库结算成功后，才向客户端输出 DONE。
- SSE 采用同步、有界事件读取；不新增队列或生产者 goroutine。初期不重试、不 fallback。

## 代价与限制

单组织共享账本行会串行化同组织预算操作，是明确的一致性取舍，尚无吞吐承诺。是否需要分层额度或额度分片，要先测量再决定。

派发标记和外部 HTTP 请求无法在一个数据库事务原子完成，因此崩溃可能导致保守占用。原型宁可进入人工/后续对账，也不冒险退款；还未实现供应商账单对账、租约、后台调度、outbox 消费和估算终态后的更正账目。

超出预留上界的 usage 被拒绝结算，保留占用，说明价格或供应商契约失效；不能声称此时实际供应商成本仍受硬上限保护。生产前必须实现超额告警与真实成本记录，并限定可保证成本上界的模型。

当前固定组织作用域，不实现用户认证或业务授权。没有面向公网的网关程序；实际 HTTP 链路由集成测试启动并关闭。本原型不能用于生产接入。

## 后续验收

增加真实身份、权限、单供应商适配和价格/tokenizer 校验；验证进程强制终止、并发恢复工作器、数据库故障切换、负载容量，再决定是否提升为生产基线。
