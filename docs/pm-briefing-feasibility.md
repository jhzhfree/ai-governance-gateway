## Q1 基于开源：为什么不直接 fork？

**结论**：开源网关解决的是"把请求转发到大模型"，这是商品化能力；我们的差异化（预算硬上限、内容审计、准入治理）恰恰是开源项目最弱的部分。所以策略是**自主内核 + 借鉴开源**，而不是整仓 fork。

**要点**：

- 候选里 LiteLLM（Python）供应商覆盖最广，但 Python 运行时的内存和多进程形态不适合低端 ARM 盒子；One API 类项目审计与预算原子性弱。
- Go 单二进制 + PostgreSQL：交叉编译直接支持 ARM64/x86_64，盒子交付最省事。
- 开源的真正价值是供应商协议差异、SSE 边界、usage 缺失这些"坑"——我们把它当**对照测试**（同请求分别打 LiteLLM 和我们的网关，比对行为），而不是把它的运行时搬进来。
- fork 的隐性成本：上游升级冲突、许可证/商标复核、以及"开源没有的 70% 我们都得重写"。

**周期/边界**：选型不阻塞 1.0；若 2.0 需要超大规模 L7 多租户，再评估 Envoy AI Gateway/Higress 作数据面。

## Q2 Token 治理与计费：技术上可行吗？

**结论**：可行，且最难的部分已有验证——按"预留→派发→结算"三段式，花一块钱扣一块钱，崩溃不多扣不少扣，超预算硬拒绝。

**要点**：

- 预算是**事务级原子预留**（数据库锁 + 约束保证），不是"事后统计扣余额"，这是与多数开源项目的本质区别。
- 供应商失败进入"不确定"状态保留占额，宁可保守也不虚账；配套人工对账闭环（标准账单导入、双人审核）。
- 1.0 要补的是产品化：预算调整 API、月度周期轮转、价格目录入库（现在价格是配置文件，调价要重启）。
- 必须接受的取舍：预留按"输入上界 + max_tokens"算，短请求会占着超额度的额度；1.0 用额度安全系数消化，不做分段预留。

**周期/边界**：预算调整+轮转约 3–5 人周；对外可以承诺"预算不超额"，不能承诺"精确到分的实时计费"。

## Q3 内容审计（主任重点）：能存、怎么存？

**结论**：已经做到第一步——加密内容审计 MVP 已实现并通过 125 个后端测试与 9 个浏览器场景：项目默认关闭、显式开启时要求填写告知依据，AES-256-GCM 信封加密、独立审计员（owner 也不自动能解密）、查看填理由且留痕、组织级哈希链可验证、到期拒读与分批清理。这是**同步封存 MVP**，还不是生产级审计平台。

**要点（已实现）**：

- 请求在准入/预算/派发**之前**原子加密写入；故障返回 503，不派发、不占预算——保证"要审计的业务一定先落审计"。
- SSE 只在内存维护有界前缀 + 完整已观测流的 SHA-256，封存成功后才发 `[DONE]`；不逐 token 写库。
- 加密按组织/密钥版本独立 DEK，AAD 绑定请求与策略快照；支持多版本轮换；主密钥遗失无管理员绕过通道。
- 保留 30 天默认（1–90 可配）、单条 64 KiB 默认（1–256 KiB 可配），记录固定保存策略版本与到期时间。
- 独立 `content-audit verify` 命令验证哈希链连续性，不需要主密钥；正文按分区表存储，查看正文只进组件内存、不进缓存。

**要点（尚未实现，属于生产加固）**：

- 异步 spool/崩溃零丢失承诺（当前硬崩溃会丢内存中未封存的回复）。
- 按月分区自动维护（当前只有默认分区 + 按行清理）、KMS 集成、自动外部不可变锚定（当前数据库内链不能防御超级用户整体重写）。
- 双人导出/批量接口（当前刻意没有批量解密）。
- 生产容量压测、清理与备份恢复演练。

**周期/边界**：生产加固约 4–8 人周（需团队校准）；容量按 `平均字节 × 请求率 × 86400` 估算（评估文档 4.3.7 算例 0.35～21 GB/天），**先实测再报数**；合规确认（告知/留存/删除）仍是上线门禁。

## Q4 审计的合规风险怎么答？

**结论**：技术方案必须等法务三个确认才能上线：员工/用户**告知**、**留存期限**、**删除与备份销毁**。

**要点**：

- 存正文 ≠ 可以随便看：分级保留（元数据长、正文短，如 30/90 天两档）、按组织开关、默认关闭。
- prompt 里经常有第三方个人信息，留存策略要按"可能包含他人数据"设计。
- 前置冲突要明说：当前产品定位"默认不存正文"是隐私卖点，审计开关打开是产品立场调整，要写进合同与隐私政策。
- 数据出境红线：护栏/审计若走境外 API，等于内容出境，与"大陆驻留"卖点冲突，1.0 明确不允许。

**周期/边界**：法务确认是 Go/No-Go 门禁第一项，不通过不对外讲"可审计"。

## Q5 护栏：做不做？

**结论**：1.0 不做功能，只留两个挂点（请求前/响应后）。这是资源决策，不是能力问题。

**要点**：

- 自研模型型护栏 = 标注、误杀、对抗、持续更新的长期投入，小团队养不起。
- 外接护栏服务 = 每请求增加 100–500ms 延迟 + 按次付费 + 内容出境合规 + 供应商可用性叠加。
- 如果 2.0 要做，先做规则型（关键词、正则、长度、PII 模式），模型型交给客户自带服务。
- 对外话术统一为"**预留了护栏扩展点，按需接入**"，不说"内置护栏"。

**周期/边界**：挂点随 2.0 插件 SDK 交付；单独做约 2–3 人周。

## Q6 准入凭什么是护城河？

**结论**：护城河不是限流参数，是**治理闭环**：企业身份 → 申请审批 → 最小授权 → 每次拒绝可解释 → 全程留痕。

**要点**：

- 限流/并发控制是商品化能力，开源都有；但"谁能用哪个模型、额度多少、谁批的、为什么被拒"这条链路开源做得很浅。
- 技术上都在现有组织/项目/角色模型上扩展：SSO/SCIM、审批流、密钥轮换与归属、审计导出。
- 审计与准入天然互相加持：准入决策进审计，审计查看也要过准入——形成闭环而不是两个功能。

**周期/边界**：随客户真实流程设计走，估算 6–10 人周；这是销售差异化叙事的重点，应放进 PPT 主线。

## Q7 2.0 扩展能力怎么保证？

**结论**：架构上按"内核稳定 + 边缘可插"设计：账本/审计的语义不改，新能力走三层扩展点。

**要点**：

- 插件挂点固定三处：鉴权后、派发前、响应后；编译期注册、禁止动态加载任意代码（安全边界）。
- 策略引擎把运营规则变成可版本化配置（优先 CEL，轻、可审计），而不是改代码。
- 路由升级是**架构级**改造（多 attempt 账本、按最坏成本预留、SSE 首字节后禁止回退），已在评估中给出方案；不承诺为"一个开关"。
- 兼容层保持 OpenAI 兼容，客户应用不因我们升级而改代码。

**周期/边界**：插件 SDK + 策略引擎 + 路由约 25–40 人周（2.0 单列预算）。

## Q8 硬件盒子：ARM/x86、低端到高端能做吗？

**结论**：能。Go + PostgreSQL 的技术栈对 ARM64 和 x86_64 都是原生支持，真正要管理的是**低端机型的资源红线**和**交付形态**。

**要点**：

- 三档规划（数字是待实测假设）：低端 ARM 8 核/4–8GB，目标 5 rps、审计保留 30 天；中端 16 核/16–32GB，约 16 rps、保留 90 天；高端 x86 64GB，约 50 rps + 对象存储分层。
- 低端红线：**eMMC 不能做审计主存储**（每天十几 GB 写入一年就磨穿寿命），必须 SSD；并发与保留期限写死在型号定义里，超卖现场一定出事。
- 离线是硬需求：现在只有企业 OIDC 登录，盒子必须先补**本地管理员**，否则开箱无法初始化。
- 交付形态：1.0 单机（只读系统 + 独立数据分区 + A/B 升级回滚），离线许可证（签名绑定硬件指纹）；高端再谈外置数据库/HA，**单盒不承诺高可用**。

**周期/边界**：交付件 + OTA + 许可证约 8–12 人周；容量数字必须先用目标机型实测，再写进报价单。

## Q9 1.0 要多少人、多久？

**结论**：加密内容审计 MVP、成员管理 Web、推理模型发现已在内核上完成；1.0 剩余增量约 **23–37 人周**（1–2 名研发 2–3 个月量级），不含硬件认证、法务和真实供应商联调。原 33–49 人周是完整目标的估算，不能按已完成的测试直接折减，此数字需团队校准。

**已完成（不再计入）**：审计捕获/加密/分权/哈希链/到期清理、审计 Web 与 CLI、成员管理 UI、`GET /v1/models`。

| 剩余工作流 | 人周（估算） |
| --- | --- |
| 审计生产加固（spool/月分区/KMS/外部锚定/双人导出） | 4–8 |
| 审计容量压测与恢复演练 | 并入下行演练项 |
| 本地身份/离线 | 4–6 |
| 预算调整/轮转 | 3–5 |
| 部署与盒子交付件（OTA/许可证） | 8–12 |
| 性能/故障/备份演练（含审计恢复） | 4–6 |

**建议节奏**：低端机实测 + 审计恢复演练（2–3 周）→ 本地登录 + 预算调整（4–6 周）→ 盒子交付件 + 门禁验收（3–4 周）。

## Q10 最大的风险与需要领导拍板的事

**结论**：技术风险都可控，真正的决策风险是"在没有法务确认和硬件实测前对外承诺"。

**风险前三**：

1. 低端盒子 I/O 瓶颈（审计是写密集业务）→ 用实测数据定价，限制并发与保留。
2. 审计被当"全量日志"卖，成本失控 → 分级保留 + 截断 + 哈希，按组织配额。
3. 2.0 路由破坏预算正确性 → 决策前置 + 最坏成本预留 + attempt 级账本，按评估方案走。

**需要拍板的 8 件事**（评估文档 12.1 节）：审计默认开关、正文保留档位、谁能看正文、失败是否阻断、是否承诺离线部署、低端并发与价格带、路由是否进 2.0、护栏对外话术。

## 附录：口径红线（对外回答时不可越过）

1. 不承诺"生产可用"——真实供应商/企业 IdP/驻留验收未完成前，只能讲"可内网试用/受控试点"。
2. 不承诺任何未经实测的吞吐与容量数字（5 rps / 50 rps 都是目标值，不是承诺值）。
3. 不承诺"智能路由/自动回退"进 1.0。
4. 不承诺"内置护栏"，只讲"预留护栏扩展点"。
5. 不承诺单盒高可用；讲备份恢复与 RTO/RPO 演练结果。
6. 讲"审计"必须区分**管理审计**（谁改了配置）与**内容审计**（输入输出正文），两者能力与合规边界不同。
7. 许可证：除已核验的 Bifrost/LiteLLM 外，其他开源组件"具体许可证需逐一复核"，不直接说"全部可商用"。
