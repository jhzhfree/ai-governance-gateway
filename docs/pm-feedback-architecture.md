## 0. 总体判断（先说结论）

1. **产品定位与技术现实基本匹配，但 PPT 有三处口径需要修正**：审计应表述为"MVP 已实现、生产加固进行中"；容量数字未实测前不能写死；盒子必须标注"单机、非高可用"。
2. **最小闭环"token 治理 + 审计"技术上已经打通**：预算原子预留/结算、加密内容审计 MVP、密钥与准入都有代码与测试证据，不是 PPT 愿景。
3. **最大的技术风险不在"能不能做"，在三处**：审计的崩溃完整性（无 spool）、低端盒子的存储 I/O、合规与真实供应商验收缺失。
4. **PPT 与技术现状有三个口径冲突，评审前必须澄清**（见 4.1）：开源复用 vs 自研内核、审计"摘要" vs 已实现的加密全文、旁路部署 vs "只改 base_url"。

## 1. 产品技术架构应该怎么做（核心建议）

### 1.1 总体形态：不要做成微服务，坚持"模块化单体 + 单一权威数据库"

```
客户端(OpenAI 兼容 SDK) ──> 反向代理(TLS) ──> 网关进程（单二进制）
                                              ├─ 协议层：/v1/chat/completions、/v1/models
                                              ├─ 治理链：鉴权→准入→审计预写→预算预留→派发→结算→审计封存
                                              ├─ 管理面：/api/v1/...（RBAC、密钥、预算、审计、对账）
                                              └─ Web 控制台（静态托管）
                                                      │
                                              PostgreSQL（唯一权威：预算、限流、熔断、审计、账本）
```

理由（可直接回应"为什么不用开源网关拼"）：

- 治理正确性依赖跨表事务（预留、限流租约、审计链同库原子提交）；拆微服务会破坏"花一块钱扣一块钱"的可证明性。
- 单二进制 + 嵌入式部署是硬件盒子（ARM 低端 4GB）的硬约束；Python/Java 多组件栈在低端机型上不可控。
- 开源项目（LiteLLM 等）作为**协议语义与兼容性对照**使用，不作为运行时底座。

### 1.2 请求治理链的固定顺序（架构的"骨架"，不许插件打乱）

```
鉴权(项目密钥) → 模型/币种校验 → 准入(限流+并发租约, fail-closed)
→ 内容审计预写(开启时, 失败=503 不派发) → 预算预留(组织→项目两级账户锁)
→ 路由选择(1.0 固定别名) → 供应商适配 → 结算(成功/不确定)
→ 审计封存(SSE 在 [DONE] 前完成) → 响应
```

要点：审计预写在预算之前，保证"开了审计的业务一定先落审计"；熔断、驻留证据校验横切在各环节。

### 1.3 内容审计管线（主任关注点，按两阶段讲）

**已完成（同步 MVP）**：项目级开关 + 告知依据（consent_ref）、AES-256-GCM 信封加密（组织级 DEK、多版本轮换、AAD 绑定请求与策略快照）、独立审计员（owner 不自动可解密、查看填理由并留痕）、组织哈希链（`verify` 命令可校验）、保留期/截断上限可配、到期拒读与分批清理、SSE 有界前缀 + 全流 SHA-256。

**生产加固路线（2–3 个月内要做完）**：

1. 本地 spool + 异步重放：消除"崩溃丢内存回复"的审计空洞，spool 满则 fail-closed。
2. 按月分区自动维护：当前默认分区 + 按行清理撑不起长期运行。
3. 主密钥进 KMS/TPM（当前是部署秘密注入），自动外部锚定哈希链头。
4. 双人审批导出、容量压测、备份恢复演练。

**明确不做的**：内容安全审核模型（护栏的"内容理解"部分）、境外护栏 API、跨项目批量解密。

### 1.4 路由与 2.0 扩展：提前把"扩展点"定死，而不是留白

- **1.0**：模型别名 → 固定供应商路由（已实现），无自动回退——这是特性不是缺陷，保证账本可解释。
- **2.0 路由**：决策前置到预留之前，按候选集最坏成本预留；多 attempt 账本 `(request_id, attempt_no)`；SSE 首字节后禁止回退。这是一次账本语义改造，PPT 中不要写成"配置开关"。
- **插件点固定三处**：鉴权后、派发前、响应后；编译期注册、禁止动态加载代码。护栏、DLP、自定义审计加工都挂在这三点上。
- **策略引擎**：限额/路由/审计策略用版本化规则（优先 CEL），运营调整不改代码。

### 1.5 硬件盒子形态（分档交付）

| 档位 | 形态 | 关键约束 |
| --- | --- | --- |
| 低端（ARM 8 核/4–8GB） | 单机 systemd，审计保留 30 天、并发限死 | 必须 SSD（eMMC 会磨穿）、先补本地管理员账号、目标 5 rps 需实测 |
| 中端（ARM 16 核/16–32GB） | 同上 + 更长保留/更高并发 | 审计写放大是主要瓶颈 |
| 高端（x86/64GB） | 网关多实例 + 外置 PostgreSQL | 才能谈高可用；单盒永不承诺 HA |

共同件：A/B 分区升级回滚、离线许可证（签名绑定硬件指纹）、只读根文件系统、本地 NTP。**当前仓库还没有这些交付件，是 1.0 尚未开始的最大工作块（8–12 人周）。**

## 3. 存在的缺陷（评审必须如实呈现的清单）

### 3.1 审计相关（主任追问概率最高）

1. **崩溃完整性**：硬崩溃时内存中未封存的回复会丢失，当前无 spool/重放——对外只能承诺"请求侧先落审计 + 崩溃可核查"，不能承诺"输出零丢失"。
2. **防篡改边界**：哈希链在数据库内部可验证，但**防不住数据库超级用户整体重写**；外部不可变锚定未实现。
3. **分区运维**：正文表只有默认分区，月度滚动创建/归档未做，长期运行有容量与清理风险。
4. **合规前置**：告知、留存、删除三件事没有法务书面确认前，审计功能不能作为商用承诺。

### 3.2 治理与运营

5. 预算保守预留导致"占用 > 实际花费"，客户观感是"额度虚高"；缓解靠安全系数，根治靠分段预留（2.0）。
6. 无预算周期自动轮转、无在线调整 API（账单月初要人工干预）。
7. 价格是启动配置文件：调价需重启且多实例需同步，存在"同请求不同价"窗口。
8. 管理 API 错误 `message` 直接等于 `code`，第三方集成体验差（发布前应改）。

### 3.3 交付与运维

9. 无 Dockerfile/Compose/K8s、无 OTA、无离线许可证——**盒子交付件为零**，这是 1.0 剩余最大工作块。
10. 无 Prometheus/OTel：指标实例级且重启清零，现场排障能力弱。
11. 无本地账号体系：离线盒子开箱无法初始化（依赖企业 IdP 在线）。
12. 单机非高可用；滚动发布需先摘流（优雅关闭 10s < 流式 120s）。
13. 低端盒子若配 eMMC，审计写入一年内会磨穿存储——BOM 必须 SSD 起步。

### 3.4 验收缺口（不是代码缺陷，但阻塞商用）

14. 三家真实供应商/真实账单/大陆驻留证据：未验收。
15. 未做容量压测与备份恢复演练：**所有性能数字目前都是目标值**。
16. 企业 IdP、原生钥匙串、生产安全专项：未验收。

## 4. 给 PPT 的具体修订建议（已逐页核对 v1.0 全 41 页）

### 4.1 三个必须先澄清的技术口径（PPT 与技术现状直接冲突）

1. **"开源打底"（P5/P28/P31）vs 实际自研内核**：现有产品核心是自研 Go 网关（治理、审计、准入对接都已在代码里），不是"吸收 LiteLLM 等成熟框架"二次开发。两种口径会导致研发预算、人力测算与闸门 1 判据全部失真。建议统一为："**参考开源语义、保持 OpenAI 兼容，治理与审计内核自研**"——这也与 P8 上"开源水土不服"的论证自洽（既然论证了开源不能用于生产，就更不能拿它当底座）。
2. **审计存"内容摘要"（P16/P24）vs 已实现"加密全文 + 分权解密"**：摘要是降级承诺，加密全文是更强且已实现的能力。建议 P16/P24 改为"**加密存储、独立审计员授权、按需解密、全程留痕**"，同时把留存期限/告知依据写进合同附件（实现里已支持 consent_ref 与 1–90 天保留配置）。
3. **"旁路/网桥部署"（P27）vs "应用只改 base_url"（P20）**：大模型 API 全程 TLS，旁路镜像拿不到明文；终端改 base_url 指向网关，本质是**显式代理/反向代理**。两种模式的流量接管、证书与网络方案完全不同，交付设计无法同时满足。必须二选一（建议：显式代理为主，"旁路"仅指网关可旁挂于出口而不改变流量路径的部署位置）。

## 附：一页话术（主任问"技术上到底行不行"时的 60 秒回答）

> 行，而且核心闭环已经不是纸面方案：预算硬上限（花一块扣一块、崩溃不多扣）、加密内容审计（默认关闭、显式开启、信封加密、独立审计员、防篡改哈希链）、准入与密钥治理都已有实现和测试证据。
> 架构上我们选择 Go 单体 + 单一数据库，而不是拼开源网关，原因有三：治理正确性依赖跨表事务；盒子要求单二进制低内存；开源的价值我们通过兼容性对照测试吸收，而不是引入它的运行时。
> 剩余风险集中在三件已排期的事：审计崩溃完整性与外部锚定的生产加固、低端盒子的实测定价、以及合规与真实供应商验收。这三件没闭环之前，我们对外的承诺口径是"可受控试点"，不是"生产可用"。
