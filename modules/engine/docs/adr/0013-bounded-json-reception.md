# ADR 0013：Chat/Responses 原始 JSON 有界接收

状态：开发实现与针对性检查；完整门禁及远端 CI 见根交付记录。接续 ADR 0012 已复现的 SDK capture 边界。

## 发现与选择

固定 Core v1.14.1 的 `HandleProviderResponse` 在返回 RawResponse 前压缩 JSON。新增实际 HTTP 回归首先复现：超限空白、gzip 解压后的超限空白、错误媒体类型和无效 UTF-8 可被接纳，原始 usage 空白被改变。这些失败没有计入通过。已发布事件仍按已有字节和摘要解释，不重新压缩或迁移历史证据。

检查了公开 `HandleOpenAIChatCompletionRequest` 的自定义响应处理入口：其回调在 `FinalizeResponseWithLargeDetection` 的正常正文解码之后执行，因此仅追加回调不能证明解析/解压前的大小边界。未设置 SDK 注明为内部使用的 large-response context，也未引入企业插件、运行时反向代理或整份 SDK fork。

将当前受控 JSON 子集收敛到已有 SSRF-safe HTTP 客户端、固定供应商 profile 与生命周期，和 Embeddings 共用一个有限接收函数。每次业务请求只进行一次物理 POST，无回退或影子调用。此变更没有增加通用供应商框架、路由器、钱包或身份系统。

## 实际复用范围与维护代价

继续直接使用固定 SDK 的公开 `network` 客户端、OpenAI 请求/响应类型、成功状态中的错误识别、响应字段规范化；其他治理、Responses 公共转换和完成日志复用本仓已有代码。受控 Chat JSON 的网络请求不再经过 `core.Init`/`ChatCompletionRequest`，移除不再使用的 Account/worker pool；并发、在途排空和凭证快照仍由现有执行池负责。

这缩小了 Core 的执行复用范围，不能再把 SDK 的完整供应商调用、Key 调度或插件能力列作产品已有能力。代价是对明确支持的固定协议维护接收契约；目前共用 JSON 接收器与已有 SSE 接收器即可满足本轮边界。未来扩展若需要大量重写供应商协议，必须按 V2 规划重新评估 SDK/小范围上游补丁的成本，不自动扩大为自建通用引擎。

## 接收与证据契约

- 仅 HTTP 200、application/json、未压缩或 identity 正文；请求显式设置 Accept 和 Accept-Encoding。固定 HTTPS/TLS/SSRF、无重定向策略保持。
- 初始响应头 10 秒、每次读空闲 3 秒、整次网络调用最多 120 秒；上层更短截止时间优先。取消和执行器关闭回收上游连接及租约，原始错误内容不外泄。
- 已声明长度超过 1 MiB 立即拒绝；未知长度/分块最多读取 1 MiB+1 字节后判定，原始空白也计数。SDK 解码前检查 UTF-8，拒绝压缩，避免从压缩包大小推测解压上限。
- 原始单候选的 index、message、finish_reason 必须无歧义，重复字段、混用 delta、空 index 或不支持字段拒绝。原有顶层重复字段、完整终止原因和数值用量检查继续适用。缺用量保持未知，不合成免费事件。
- SDK 响应的 ExtraFields 整体重置，只临时传入本接收器实际获取的 RawResponse；上游伪造内部字段不能成为可信响应头、费用或来源元数据。离开适配层前清除原始响应，仅保留独立数值 usage 的精确原始字节作为持久证据。
- 新事件中 usage 对象内部空白、顺序和数字字面值不变；Record/Recover 按原字节摘要和冻结绑定验证。旧事件不改写。完成事件、结算回执和客户端结果保持各自语义。

## 验证与未完成项

实际 HTTP 故障覆盖原始超限、分块超限、压缩、媒体/编码、重定向、尾随文档、无效 UTF-8、200 内错误和候选歧义；原始 usage 精确保留、内部字段伪造、空闲/取消/关闭回收通过专项检查。三协议治理矩阵增加超限 JSON 和错误媒体，断言单次派发、无完成事件/回执、未知费用占额；正常 JSON/SSE 直接核对数据库原始 usage 字节。已有实际 SIGKILL、权限、预算、审计、SDK 和浏览器链继续回归。

本轮没有新迁移、依赖版本变更、new-api 代码复制或生产操作。真实供应商、容量、商业来源核验仍独立验收；不将协议接收修复称为 V1 完成。
