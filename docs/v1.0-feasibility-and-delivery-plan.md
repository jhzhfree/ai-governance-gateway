## 一、整体技术可行性

### 1.1 结论

**可行，且核心闭环已不是纸面方案。** 评审文档（基线 `6e58179`）列出的 PPT 七大功能，截至目前全部有代码与测试证据；当时的三大技术风险中，"审计崩溃完整性"已闭环，其余两项（低端盒子实测、合规确认）是验收动作而非开发风险。剩余工作集中在**交付件**（安装、升级、许可证、盒子产物）与**外部依赖对接**（JH-SAC/DAS 真实协议、厂商官方账单、企业 IdP），不在"能不能做"。

| PPT 功能 | 评审基线状态 | 当前状态（阶段 1–11 验收后） |
| --- | --- | --- |

### 1.3 三大风险现状

| 评审时的风险 | 现状 |
| --- | --- |
| 审计崩溃完整性（无 spool） | **已解决**：同步加密暂存检查点、崩溃后租约恢复、过期清理，专项覆盖 SIGKILL/并发恢复/篡改拒绝 |
| 低端盒子存储 I/O 与容量 | 未变：仍是"实测前不承诺"，属验收项；BOM 强制 SSD 的建议继续有效 |
| 合规与真实供应商验收缺失 | 未变：三家真实供应商/官方账单/大陆驻留证据/合规三确认，外部环境待提供 |

### 1.4 明确不做或移出 1.0（维持评审口径）

自动降级路由（账本改造，2.0）、自研内容护栏模型（仅保留三个编译期扩展点）、多模态/工具调用/Embedding、单盒高可用。这些是边界声明，不是技术失败。

## 三、v1.0 剩余工作量与排期（1–2 人 × AI 工具）

### 3.1 V1.0 核心范围定义

已验收部分（阶段 1–11：治理主链、加密审计与崩溃恢复、本地身份、设备准入基础、部门层级与成本、预算双人审批、指标导出、关键字匹配）不再计入工作量。**剩余 V1.0 核心 = 下列 A–F 六个工作块 + G 验收**；自动降级、目录同步、护栏、OTel 明确不进 1.0。

### 3.2 剩余工作块与估算（净开发人周，AI 辅助口径）

| 块 | 内容 | 估算 | 依赖 |
| --- | --- | --- | --- |
| A 审计生产加固收尾 | 月度分区自动维护、双人审批导出、哈希链外部锚定（文件/独立介质即可）、KMS 抽象接口 | 2–3 人周 | 无 |
| B 终端准入收尾 | 浏览器管理端设备审批、出口控制、mTLS/TPM 可选档、SAC/DAS 协议适配层 | 2–3 人周 | **SAC/DAS 契约冻结**；适配层可先按评审假设开发 |
| C 关键字匹配收尾 | 规则管理页面完善、流式输出边界固化（仅告警）与文档口径 | 0.5–1 人周 | 无 |
| D 报表与通知 | 官方账单适配框架 + 首个厂商样本、预算告警外部通知通道（境内邮件/webhook） | 1.5–2.5 人周 | **厂商官方账单样本**（外部） |
| E 盒子交付件 | 安装/升级脚本、A/B 分区或整盘镜像方案、离线许可证（Ed25519 绑硬件指纹）、容量实测工具与报告模板 | 4–6 人周 | 需要 1 台目标硬件做实测 |
| F 运营收尾 | 管理 API 错误 message 与 code 分离、部署文档补全、打包与变更记录 | 1 人周 | 无 |
| **小计（开发）** | | **11–16.5 人周** | |
| G 验收（非编码） | 三家真实供应商 + 真实账单、备份恢复演练、低端机 IOPS 实测、合规三确认 | 2–3 人周（挂墙时间受外部约束） | 外部环境 |

### 3.3 排期方案

**方案一：2 人（推荐）≈ 9–11 周**

- 甲（后端向）：A → B（适配层先行）→ D → G 配合；乙（交付/全栈向）：C → E → F → 与甲交叉复核。
- 关键路径是 **E（盒子交付件）**，必须第 1 周就排队目标硬件，实测不要压到最后。
- B 的 SAC/DAS 对接存在外部等待，契约未冻结时甲转做 A 的 KMS 接口与 D 适配框架，总周期不被卡死。

**方案二：1 人 ≈ 16–20 周（约 4–5 个月）**

- 顺序：C（1 周内见效）→ A → D → E → B 适配层 → F → G。
- 风险：单人无法并行"开发"与"验收"，G 的外部等待会直接拉长挂墙周期；建议至少把实测硬件的申请与合规确认在第一周发起。

**AI 辅助系数的依据**：本仓库近期实际节奏即"1–2 人 × AI 工具"——11 个验收阶段（每阶段含后端、Web/CLI/TUI、契约冻结与浏览器场景）在数周内交付，且每阶段都通过 205 项顶层测试 + race + 17 个浏览器场景的门禁。估算已按此观察值校准，不再另打折扣。

### 3.4 AI 辅助开发的红线（确保速度不牺牲质量）

1. **门禁不可绕过**：AI 生成代码一律过 `scripts/verify.sh`（gofmt、API 契约冻结、vet、race 测试）与浏览器场景，未过不合入。
2. **人审安全敏感模块**：加密/审计哈希链/身份与令牌/权限回收四类改动必须人工逐行复核，AI 只做初稿与测试补全。
3. **迁移只增不改**：0022 之后的数据库变更继续遵循 append-only 规范，由 AI 起草、人审锁语义（FOR UPDATE/行锁/租约）。
4. **每块工作按"可独立验收阶段"切分**，先验收再推进——与阶段 1–11 的节奏一致，避免 AI 加速带来的集成倾塌。

### 3.5 外部依赖清单（PM 推进，决定 G 的挂墙时间）

1. JH-SAC/JH-DAS 设备状态与身份映射接口契约（阻塞 B 的真实验证，不阻塞编码）。
2. 厂商官方账单样本至少一份（阻塞 D 的真实适配）。
3. 目标低端硬件 1 台（阻塞 E 的实测报告）。
4. 法务对告知/留存/删除三确认（阻塞审计功能的商用承诺，不阻塞开发）。
5. 企业 IdP 或生产 OIDC 环境一轮验收。

## 附：一句话结论

> 技术可行性已经从"论证"变成"证据"：七大功能全部有验收记录，评审时的最大风险（审计崩溃完整性）已闭环。剩下 11–16.5 人周的开发量，2 人 × AI 工具 9–11 周可完成 V1.0 核心；真正决定上线时间的不是代码，是 SAC/DAS 契约、官方账单样本、实测硬件与合规确认这四件外部事——它们应当本周就启动。
