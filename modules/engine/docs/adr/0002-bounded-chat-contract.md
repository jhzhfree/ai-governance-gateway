# ADR 0002 有界 Chat 请求与计量证据

状态：已实现，V1 隔离执行模块；尚未接入主网关。

## 问题

Bifrost Core v1.14.1 的 OpenAI 转换会把小于 16 的 max_completion_tokens 提高到 16（providers/openai/chat.go，MinMaxCompletionTokens）。外部授权/预算若按原始值计算，会与实际派发上限不一致。SDK 同时支持超出当前产品验收范围的参数和文件 URL 解析；不能把 SDK 能解析等同产品已支持。

## 决策

1. 必须显式提供 max_tokens，至少 16，不得超过服务端 Config.MaxOutputTokens。默认上限 4096，配置范围 16—1,000,000。小于 16 的请求直接拒绝，不静默增加预算或上游上限。请求实际派发参数保留 16 的边界已有 HTTP 断言。
2. 当前仅接收 model、messages、max_tokens、stream、tools、tool_choice、n；n 只允许 1。模型必须匹配服务端配置。顶层和受校验的消息/工具对象拒绝未知、重复、大小写变体字段。工具参数 JSON Schema 和 arguments 字符串属于用户数据，不进行同样的字段白名单处理，也不执行工具。
3. 消息最多 64 条、单条文本最多 16 KiB，总请求保留 1 MiB 限制。支持 system/user/assistant/tool；拒绝多模态数组和文件 URL 内容，防止未验收的 SDK 附加取数行为进入主链路。工具定义与历史调用仅允许 function；数量、名称、调用 ID 和参数字符串有界。
4. 用量须非负、输入不超过 2,000,000、输出不超过本请求授权上限，总量等于输入加输出。非零证据必须有正输入数。SDK 合成的全零对象继续视为未知。金额计算、币种、价格快照、最终结算仍由主项目账本处理。

## 兼容性与待办

这是刻意收窄的验证协议，不能宣称完整 OpenAI 兼容。temperature、top_p、max_completion_tokens、Responses、嵌入、多模态等尚未放行；需要契约及治理测试后逐项扩展。低于 16 的旧链路请求是迁移兼容性问题，切换前必须解决或在模型能力中明确展示限制。

用量来自 SDK 规范化对象，仍不是带完整来源证明的原始供应商账单。部分字段被 SDK 补默认值时，单靠总量相等不能证明来源完整；接入权威结算前还须增加原始 usage 存在性和价格维度证据。上游 usage 缺失与计费状态未知不自动释放预算。

当前工具测试仅证明定义和历史结果传递；输出工具调用、SSE 参数增量以及完整多轮闭环还需验证。退出/过载、双节点、真实供应商及性能门禁均不因本阶段通过而标记完成。
