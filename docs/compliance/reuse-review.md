# 单进程分支复用与来源核验

2026-11-07，开始实施 V2 后的首轮核验。此记录是开发证据，不是商业授权结论；没有更改第三方许可证，也没有给整个自有仓库擅自添加开源许可证。

## 已收集的证据

- 基线为治理工程 `701317de40cfe7eb27b0120e5e73443ea79afd3d`；本轮只修改自有入口、控制台和文档，不复制 new-api 源码或引入新运行时依赖。
- `modules/engine/go.mod` 固定 Bifrost Core `v1.14.1`。本地模块缓存中的 `LICENSE` 为 Apache License 2.0；实际导入图中包含其供应商 SDK 依赖，不能只审核 Bifrost 一个包。
- 对 Linux/amd64 的 `gateway-engine` 执行 `go list -mod=readonly -deps`，收集第三方模块的固定版本、顶层许可证/NOTICE 文件及 SHA-256，见 [依赖基线](dependency-baseline.json)。这是导入图清单，尚不是链接后二进制 SBOM；未包含 Go 标准库、系统库和容器基础镜像。
- Web 继续使用锁定的 React、TDesign 和原业务页面。依赖基线按锁文件的 dev 标记区分声明；其中构建/测试依赖有 MPL-2.0、CC-BY-4.0 等，不能将所有依赖都笼统声明为 MIT。`dev` 不证明其代码或素材一定未进入产物，发行前仍需检查实际 bundle。
- 本轮导航 SVG 使用本地简单几何路径，没有下载图标、字体、图片或照搬第三方控制台。未改 npm/Go 依赖版本。

## 发行前尚须完成

1. 继承代码逐文件来源、贡献权属和嵌入素材核验。仓库当前没有顶层 `LICENSE`，公开仓库不等于所有代码已获任意商业再许可。
2. 完整收集第三方子目录 NOTICE/许可证、Go 运行时和实际 Web bundle 归属；补齐二进制依赖及发行包 SBOM，不把当前顶层文件采样当作全量审查。
3. 确定自有产品的商业分发条款及第三方声明；实际交付镜像、配套 IdP/Agent 分别核查。未经确认不宣称“零授权风险”或已满足商业发布要求。

这些事项限制正式发行结论，不阻止已获授权的自有代码开发和本地合成验证。


## 候选包通知收集增量

本分支打包脚本增加 `scripts/collect-notices.py`：以实际生成的 Go 二进制依赖为范围，分别匹配根模块/引擎模块的路径与版本，复制可找到的顶层 LICENSE/NOTICE/COPYING 等文件和 Go 运行时通知。前端按冻结安装结果收集运行/构建包的顶层通知，缺失者写入待审清单；没有自行推导或改写许可证。包验证器要求 Core 的对应版本许可文件存在且索引哈希匹配。

这补充发行材料，不改变前文待核验项：嵌套第三方内容、实际 Web bundle 归属、文件来源与自有分发条款仍须审查。缺少顶层文件不等于无许可证，找到文件也不等于满足所有分发义务。当前仍只生成开发候选。

## 持久完成证据增量

0032 迁移、`internal/completion` 和对应故障测试在本分支新增，组合本仓 `budget.ReconcileTx`、编号迁移和执行接口；Bifrost 适配仅增加完成标记及持久 Store 接线。原始计量白名单依据当前已验收的 Chat 字段契约实现，没有复制 new-api 源文件或新增第三方依赖，两个 `go.mod/go.sum` 与 Web 锁文件保持不变。旧 new-api 完成 outbox 的状态机经验用于区分供应商完成、客户端状态与预算回执，但没有把旧事件直接冒充新引擎证据。

这说明本轮新增文件的实现方式，不补足继承业务模块、SDK 子依赖或最终商业分发条款的未决核验；完整门禁和源提交见交付跟踪。

## 受控 Responses 增量

本阶段直接复用仓库既有 `provider.ResponsesRequest`、`PublicResponses` 与 `gateway.responsesStreamWriter`，在执行接缝新增当前路由的持久能力检查；不复制其他项目的转换代码，也不启用 SDK 的完整原生 Responses 路径。新增真实嵌入式 SDK/流式/故障测试，沿用已经锁定的测试 SDK，运行时和前端依赖锁文件未改变。`chat_v1` 继续表示实际供应商计量格式，不新造一份 Responses 供应商计数。继承代码来源、嵌套依赖/素材、产品分发条款仍未因测试通过而自动获商业清查结论。

## 文本 Embeddings 与输入准入增量

0033、input-only 用量解析、保守文本估算与配套接线/测试在当前分支新增，复用本仓已有向量输入/输出校验、预算/审计/恢复及表单。首先验证了固定 Core 的向量请求路径；原始空白超限测试揭示 SDK capture 压缩 JSON 的边界，最终复用已有 SDK SSRF-safe HTTP client 与生命周期，在适配器内作原始有界接收，不复制或修改上游 Core，不调用其企业专用上下文接口。接口范围依据三家官方公开文档，来源链接见 ADR 0012；无新增运行/构建依赖或外部素材。

继承代码、SDK/网络库子依赖与最终商业分发条款仍按前文核验。自有新增接线不等于整个仓库已商业清查完毕。

## Chat 原始接收范围调整（2026-11-08）

按 [ADR 0013](../../modules/engine/docs/adr/0013-bounded-json-reception.md)，固定 SDK 的普通 capture 无法满足解析前边界，因此本仓复用已有网络客户端并共用有限 JSON 接收器。实际 SDK 复用为公开网络保护、类型、错误识别和规范化；移除当前不用的 Core/Account worker 调用，不再声称 SDK 全执行平台已接入。没有复制上游实现、引入新依赖或改动锁定版本；继承代码及完整商业分发权属仍待核验，历史依赖基线不代替本提交实际二进制清单。
